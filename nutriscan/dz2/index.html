Завдання курсукурс

Наскрізний проєкт NutriScan

Ситуація в проєкті

Привіт! Концепцію NutriScan ви вже опрацювали. Відбувся discovery call, і замовник підтвердив рамку MVP. Наступний крок як PM-офісу — структурувати проєкт: показати, з яких частин він складається, як вони взаємодіють у ключовому сценарії, і де закінчується підтверджене знання.

Матеріали (вхідні дані)

  • Canonical Project Snapshot після ініціації — підтверджений верхньорівневий склад MVP і цільові платформи (iOS + Android, один release train).
  • Ваш власний Lean Canvas з ДЗ №1 (працюємо на тій самій дошці Miro).

Що входить у MVP (канон)

  • Реєстрація через email + базовий onboarding.
  • Фотозйомка чітких англомовних етикеток на відносно рівній упаковці.
  • OCR/парсинг: калорії, білки, вуглеводи, жири, розмір порції (за наявності).
  • Попередження про впевненість (confidence) + ручне виправлення.
  • Коригування кількості порцій / перерахунок.
  • Збереження в Daily Log + проста історія сканувань.
  • Базові analytics-події + privacy consent.

Поза MVP (не додавати)

  • Пошук за штрихкодом (barcode), мультимовні етикетки, розпізнавання інгредієнтів/алергенів.
  • Рекомендації страв / будь-які медичні поради, social sharing, інтеграції Apple Health / Google Fit.

Правило: те, чого немає у вхідних даних, — не вигадуйте, а позначайте як assumption або open question.

Основне завдання

  1. За допомогою Mindmap складіть блок-схему NutriScan (радимо ту саму дошку Miro). Схема має показувати не лише компоненти, а й зв'язки/стрілки та базовий функціональний потік ключового сценарію: користувач → фото етикетки → OCR/ML-компонент → результат із рівнем впевненості → ручне виправлення → збереження в Daily Log.
  2. На підставі Mindmap складіть Outline проєкту в Google Docs (структура — нижче).

Верхньорівневі частини системи (рівень компонентів, без вибору стека)

  • Мобільний застосунок (UI) та типи користувачів.
  • Backend / сервіс даних — Daily Log, історія сканувань.
  • OCR/ML-компонент — розпізнавання етикетки, показ впевненості.
  • Зберігання даних + privacy consent.

Позначайте як assumption / open question те, що не підтверджене вхідними даними:
• панель управління (адмінка) для довідників поживності / модерації виправлень — у підтвердженому MVP її немає, тож це open question до discovery, а не обов'язковий елемент;
• API / сторонні інтеграції — показуйте лише підтверджені; якщо не визначені — open question.

Обов'язково покажіть (бізнес-логіка і ролі)

Типи користувачів + основний user flow + ключові взаємодії з системою — тобто хто, через що і в якій послідовності проходить основний сценарій, і які компоненти при цьому задіяні.

Структура Outline (шаблон)

Оформіть Outline у Google Docs за таким скелетом:

  • Мета проєкту (1–2 речення).
  • Scope / out of scope — що входить у MVP і що явно виключено.
  • Основні компоненти та ролі — частини системи + типи користувачів.
  • Ключовий user flow — основний сценарій використання.
  • Обмеження — платформи, якість OCR, privacy.
  • Assumptions / Open questions — зокрема адмінка та API/інтеграції.

Не додавайте строки, бюджет чи склад команди — це наступні ДЗ (планування й оцінка).

Що здати

  • Mindmap-блок-схема з взаємодіями/потоком (посилання на Miro).
  • Outline у Google Docs за наведеною структурою (у документі — посилання на Mindmap).

Обмеження та правила

  • Не виходьте за підтверджений MVP; те, що поза scope (barcode, мультимова, social), позначте як явно виключене.
  • Не проєктуйте технічну архітектуру і не обирайте конкретні технології/протоколи — досить рівня системних компонентів.
  • Схема має показувати взаємодію, а не лише перелік компонентів (уникайте статичного дерева).
  • Чого немає у вхідних даних — позначайте як assumption / open question, а не вигадуйте.

Timebox

Орієнтир: 90–120 хв — реалістично, якщо не проєктувати архітектуру з нуля. Core — обов'язкове; додаткове завдання — справді опційне.

Додаткове завдання (опційне)

Слово «scan» у брифі двозначне: клієнт іноді має на увазі barcode, хоча в MVP це — розпізнавання етикетки. Покажіть, у якому місці структури ця неоднозначність проявляється, і запропонуйте, як її зняти без розширення scope (зафіксувати як open question / майбутній change request). Підказка: цю двозначність уже зафіксовано в Артефакті 01 — Sales Handoff.

Mindmap-схема

Аутлайн

Мета: Перевірити, чи стане ведення журналу харчування достатньо зручним завдяки скануванню етикетки, щоб користувач обрав його замість ручного вводу інших продуктів.

Scope

  • iOS та Android версії застосунку.
  • Аккаунт у застосунку.
  • Реєстрація за email.
  • Онбордінг.
  • Розпізнавання англійського тексту на фото продуктів.
  • Парсінг розпізнаного тексту для аналізу КБЖУ, розмір порції за наявності.
  • Аналіз впевненості у результаті парсінгу і демонстрація її користувачу.
  • Можливість виправити результат незалежно від рівня впевненості.
  • Ведення історії сканів клієнта і збереження її у Daily Log.
  • Можливість виправити кількість з’їденої їжі.

Out of scope

  • Вебсайт продукту.
  • Сканування баркоду.
  • Навчання застосунку на відповідях.
  • Преміум акаунт.
  • Реєстрація за номером телефону.
  • Аналіз тексту не англійською мовою.
  • Поради щодо продуктів.
  • Оцінка якості продукту.
  • Інтеграція з іншими застосунками.
  • Переклад застосунку на інші мови.
  • Social sharing.

Основні компоненти

  • Аккаунт користувача.
  • Сканер продуктів.
  • Виправлення продуктів.
  • Історія сканувань.

Основні ролі

  • Зареєстрований користувач.

Ключовий user flow

  1. Реєстрація / авторизація через email (перший вхід), далі — автоматичний вхід.
  2. Користувач фотографує етикетку продукту.
  3. OCR/ML-компонент аналізує фото та розпізнає дані.
  4. Застосунок показує результат із рівнем впевненості (confidence).
  5. За потреби — ручне виправлення розпізнаних даних.
  6. Коригування кількості порцій / перерахунок.
  7. Збереження запису в Daily Log.

Обмеження

  • Платформи: iOS + Android з одного release train. Через одночасний реліз одна з платформ може чекати, поки інша пройде ревью.
  • Якість OCR залежить від глянцю, вигину упаковки, шрифту і формату етикетки - розпізнавання не гарантує 100% точність, тому передбачені confidence-попередження та ручне виправлення.
  • Продукт wellness-, не медичний - без діагностичних тверджень і рекомендацій.
  • Privacy - обов'язковий privacy consent.

Assumptions / Open questions

  • Адмінка (панель для довідників поживності / модерації виправлень) - потрібність не підтверджена, рішення залишено на майбутній discovery.
  • API / сторонні інтеграції - поки не визначені.
  • Двозначність слова «scan» - у брифі клієнта термін міг означати як фото етикетки, так і штрихкод (зафіксовано в Артефакті 01 - Sales Handoff). У цьому Outline та в user flow свідомо вжито «сфотографувати», щоб зняти неоднозначність без розширення scope. Уточнення з клієнтом - предмет майбутнього change request.
  • Склад onboarding («особисті параметри» користувача) - не визначений вхідними даними; можливе розширення після завершення MVP на запит клієнта.
  • Склад analytics-подій — Canonical Snapshot підтверджує лише загальну рамку «базові analytics-події», без переліку конкретних метрик. Кандидати, що обговорювались у команді (час сканування, частота використання, популярні продукти, модель телефону, частка виправлень, середня впевненість, факт проходження onboarding), не підтверджені клієнтом і потребують окремого узгодження. Збір даних про популярні продукти додатково потребує перевірки на відповідність privacy-політиці — не лише він, а весь перелік підлягає тому самому уточненню.
  • Мова програмування: треба визначити мову програмування для проекту, чи це буде нативна розробка, чи одна мова для двох білдів
  • Аналіз етикетки: чи маємо писати власні інструменти для аналізу, або можемо використовувати готові SDK

Додаткове завдання курсу про двозначність слова «scan» ми закрили пунктом в Assumptions: в аутлайні й user flow свідомо вжито «сфотографувати», а уточнення з клієнтом винесено в майбутній change request.
